## 1. 三種驗收不得混算

| 驗收層 | 要回答的問題 | 方法與證據 | 不能推出的結論 |
|---|---|---|---|
| A 程式契約 | 指定輸入下，有無遵守流程、權限、預算及持久化規則？ | 確定性替身、整段互動與儲存檢查、CI | 模型理解準確、實際使用者少返工 |
| B 真實模型行為 | 指定模型與版本，在具體情境下是否產生可接受內容？ | 真實 API、完整原始輸出、逐案例人工評分 | 所有模型／所有場景都有效 |
| C 使用者效果 | 多一層逗福是否降低需求偏離和返工，代價是多少？ | 公平對照、實際使用與完整成本／時間 | 僅因回答更長、格式完整或主觀喜歡就宣稱有效 |

驗證順序：A 定位程式問題 → 小規模 B 確認連線與輸出契約 → C 比較效果。GitHub 綠燈是 A 的一部分。

## 2. 案例資料與狀態

權威案例資料為 [cases_v1.json](../eval/acceptance/cases_v1.json)，含 30 個合成情境，各有前置條件、操作、可觀察期望、來源、決策依賴及證據要求。

- `execution_status: not_run`：本套案例尚未按此規格執行；不是 pass、fail，也不是預估成果。
- `readiness: ready_for_implementation`：可開始把已明確要求落到程式或評測，不等於功能存在。
- `readiness: blocked_by_decision`：列出的作者裁決尚未完成；仍可建立資料模型或保留測試情境，不能把提案當正式規則改行為。
- `related_existing_tests`：重用與檢查的入口；既有測試通過不自動等於本案例通過。
- `contract_and_live`：替身測試與真實生成的結果分開留存；前者不得替代後者。
- `contract_and_human`：欄位／格式與語意可反駁性分開評；通過非空欄位驗證不算人工通過。
- `critical` 是有限範圍工程驗收的零容忍項目提案，不是對產品無錯誤的保證。語意評估仍報錯誤率與不確定性。

## 3. 每個案例的執行規則

1. 固定 code commit、套件／模型版本、設定與 case 版本；替身執行不接觸付費 API。
2. 為每個案例建立獨立暫存案件與資料路徑，保存初始狀態；不使用正式使用者記憶。
3. 依 `steps` 操作。需要模型測試替身時，在明確介面回傳指定內容；不要略過要驗收的中間層。
4. 比對每條 `expected`；留存實際輸出與證據位置，缺少證據不得記 pass。人評可接受語意等價表達，不要求答案逐字一樣。
5. 保存 `pass / fail / blocked / not_applicable` 及原因；保留所有嘗試，不只挑成功輸出。
6. 輸出失敗、未解析、逾時與模型拒絕均留在完整分母，並依原因分列；適用的正當阻斷另依預期行為評分，不一概算模型錯誤。

建議執行紀錄欄位：`run_id, case_id, case_version, code_commit, execution_kind, provider, model, settings, started_at, duration_ms, outcome, assertion_results, evidence_paths, model_request_count, transport_attempt_count, token_usage, cost_actual, reviewer, limitation`。金額若無法取得，保留 null 與原因；不能填零假裝免費。記錄實際模型請求與傳輸重試，避免把兩者混算。

此處是執行紀錄規格，不建立帶 pass 的空白示例結果。本輪不新增結果資料夾或效果數字。

## 4. 第一批應實作的 P1 回歸情境

### AC-19：最後交付版本與驗收一致

前提：以 default/free 的執行路徑測試；第一次替身回答具體可交付，能通過 ATL-3，但包含觸發迴避重寫的片語。第二次替身回答缺少實質交付內容。

操作：執行完整 `run_one_interaction`，捕捉模型呼叫、驗收結果、最後顯示與 end 記錄。測試必須確認實際走到迴避重寫，不接受只直接呼叫 audit 函式的替代測試。

期望：第二版也要驗收；不能沿用第一版的通過紀錄。若第三次仍未通過，以真實最後狀態降級。原始輸出、顯示內容及 audit 對應同一最終版本；有效 Zone C 立場保留。

基線定位：`src/main.py` 中 `_execute_task_with_atl3_gate` 後的迴避重寫路徑。這是由程式碼讀取定位的待驗證問題；本輪未建立可執行重現測試，未聲稱已修復。

### AC-20：多種重寫共用同一預算

前提：模型交替產生缺產出物、迴避句型等不合格內容。

期望：適用 ATL-3 的最終生成階段，初次加最多兩次修正；第三次之後不能換一個重試原因再開呼叫。這個限制不冒充 /propose 前五輪或整段補位的總呼叫數。諮詢／冷卻例外需獨立驗收，不能在修正 P1 時不小心恢復自動工單要求。

退出條件：AC-19、AC-20 對應的確定性整段回歸通過，既有測試無新增失敗，且所有重寫分支在 code review 中可追溯。此批不需要先裁決三軸分類，也不需要付費模型。

## 5. 三組產品效果對照（AI 提案）

| 條件 | 設定 | 用途 |
|---|---|---|
| A 直接模型 | 同一模型與固定簡潔基礎指令，允許其正常回答／提問 | 了解基本表現 |
| B 協作提示詞 | 同模型加固定且完整的復述、缺口與確認指令，無逗福程式治理 | 分離好提示詞本身的效果 |
| C 逗福 | 同模型加已實作且公開說明的完整逗福流程 | 測試治理／記憶管線增加的效果與負擔 |

公平條件：

- 固定模型實際 ID、生成參數、工具權限及可取得的任務資訊。不同 backend 各做完整三組，不拿不同模型間的差距歸功於逗福。
- 三組可取得相同的使用者答案，採事前寫好的回應規則：問到某項缺口才提供對應事實，不特別幫逗福補資料。任務結束或互動上限以相同規則判定。
- 修正／長期記憶情境中，各組都可取得相同的確認歷史。另設「無歷史」實驗時，清楚標成記憶可得性的差異，不混在治理增益裡。
- 共用可執行的資源上限；逗福的額外呼叫、時間、token 與使用者回答次數全部計入。所有 prompt（含強協作提示詞）在保留集前凍結並可審閱，不設弱對照湊成果。
- 交付內容匿名且隨機排序交給未參與該次生成的人工評分者。移除系統品牌標記但不改動實質內容；安全／誠實提示仍保留。若格式洩漏條件，記錄盲測限制。
- AI 可協助整理，但不得以產生答案的 AI 自評代替獨立人評；爭議項由 MOMO 或另一名人工評分者裁決並保存理由。

## 6. 資料切分、指標與判斷

這 30 個公開規格案例可用於工程調校，**不能再宣稱是未見過的保留集**。初次效果試驗建議另準備至少 20 個未用於調校的多輪案件；每案三組，各重複三次。案件數量與重複次數是小規模試驗提案，不是統計充分性的保證。

保留案件與評分答案先凍結，不提供給模型的正式記憶或調校流程。允許先用少量非保留案件確認輸出可解析；這些資料不得混入效果成績。若依保留集結果改規則，該批轉為開發集，另建新的保留集。

| 指標 | 明確分母／計算 | 如何解讀 |
|---|---|---|
| 主要：需求偏離率 | 有至少一項已確認目標／硬限制被違反的任務數 ÷ 全部指定任務數 | 越低越好；同時報違反哪些條件，不只總分 |
| 任務完成率 | 在共同資源上限內達成事前驗收條件的任務數 ÷ 全部指定任務數 | 逾時／未完成保留分母；禁止靠停答降低偏離率 |
| 返工 | 每任務使用者因 AI 誤解而糾正的次數；報分布 | 使用者主動改需求、模型合理補問另外計數 |
| 記憶誤用率 | 引用錯誤／過期／其他案件／未確認記憶的任務數 ÷ 全部指定任務數 | 另報有記憶情境的分層結果 |
| 互動負擔 | 每任務澄清問句數、使用者回應次數、總耗時 | 不能只展示減少返工而隱藏多問十題 |
| 資源 | 每任務模型請求、傳輸嘗試、實際 token、費用 | 費用未取得時不推估成已實測數字 |
| 無法評分／解析率 | 無法依預定規則判分的輸出數 ÷ 全部輸出數 | 同時記失敗原因；不得排除後只報高正確率 |

不把單次回答當作相互獨立的新使用者；重複執行按原案件成組報告。提供各案配對差異、彙總差異及不確定範圍，避免小樣本被寫成普遍保證。

提案判斷規則：

1. 工程候選版：範圍內 critical 契約全部通過；blocked/not_run 不能當通過；啟用中的介入不能略過驗收。
2. 有限試用：指定模型完整流程可運作、無未處理的 critical 問題、已定義的使用與錯誤恢復流程可完成。不要求先證明普遍優越才准許小範圍試用。
3. 正面效果訊號：相較 A 與 B，C 的需求偏離較低，任務完成率不降低；返工、互動負擔、成本完整並列。樣本不確定時寫「尚未證實」，不能因點估計較好就宣稱統計上成立。
4. 只有成本或互動負擔增加、品質沒有可辨識改善：回到流程簡化與定位，不繼續用增加功能掩蓋結果。

所有判斷規則必須在效果資料產生前鎖定版本；如要加入容忍幅度或正式提升門檻，先寫明目的與依據，不在看到結果後修改。

## 7. 既有 SAV 的重用與限制

沿用 `eval/sav/sav_runner.py`、合成人物卡、資料隔離及原始回答保存方式，作為長期記憶子評測。既有卡與 gold 不在本輪修改。

先檢查 runner 與目前的供應商選擇、輸出格式是否相容。`scorer.py` 現行 `rate()` 的分母為 hit + miss，unparse 另報；新產品評測需同時提供完整分母結果，避免解析失敗被排除後顯得成績更好。歷史分數保持原口徑並標版本，不回頭無聲重算。

SAV 的選擇題改善不等於活動企劃少返工，也不等於情緒或危險識別有效。各子評測結論只用於其實際涵蓋的範圍。既有 RUN_REPORT 是當時的執行紀錄，不拿它推斷所有外部或後續實驗都沒執行。

## 8. 外部執行與交付證據

本輪無任何真實模型呼叫、付費評測、邀請使用者或部署。正式 live run 前需在適當的祕密設定位置配置指定後端，設定模型、單次與整批用量上限；不要求把金鑰貼到對話或提交至 GitHub。

線上交付須先找出現有網站部署來源與核心版本，再驗證：送出需求 → 修正理解 → 生成交付 → 查看記憶 → 停用記憶 → 重開後仍生效 → 模型失敗可恢復。若託管多人資料，再加入使用者隔離；若允許多案件，加入案件範圍驗收。沒有網站執行證據時只交付核心／CLI，不冒稱網頁已更新。

每次成果報告附：規格與 code commit、實際執行範圍、完整 pass/fail/blocked/not_run 數量、原始證據位置、未驗證事項與下一個修復批次。私人實測內容留於受控位置，不因 repo 公開就提交逐字紀錄。
